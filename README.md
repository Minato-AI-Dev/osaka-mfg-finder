# 大阪 製造機会発見ツール（Osaka Manufacturing Opportunity Finder）MVP

大阪の中小製造業が持つ加工技術と、異業種の技術ニーズを照合し、業種名やキーワードでは見つけにくい **新しい用途・取引の可能性** を提示するプロトタイプです（仮称）。

> ⚠️ **同梱のデータはすべて架空です。** 実在の企業・実在の需要を表すものではありません。
> 「既存サービスでは発見できない」という点は**未検証の研究仮説**であり、このMVPで検証するものです。

---

## 1. 検証したい仮説

| 仮説 | 内容 | このMVPでの確認方法 |
|---|---|---|
| A | 技術を名称だけでなく材料・加工能力・機能・精度に分解すると、異業種ニーズとの関連を発見できる | 構造化（STEP1/2）の結果と、キーワード検索の取りこぼし例を比較する |
| B | キーワードでは見つけにくい組み合わせを、意味検索＋LLM分析で発見できる | 「キーワード」と「AI」の上位K件を並べ、Precision@K（正解データのある需要のみ）で比べる |
| C | AIがマッチング理由と不確実性を説明すると、担当者が候補を評価しやすくなる | 画面の「推測」「不一致」「要確認」「原文」を使い、人手で有望／不適合／要確認を付ける。評価の一致度・コメントで確認する |

## 2. クイックスタート（ローカル）

前提: Node.js **22 LTS 推奨**（`.nvmrc` 参照）、npm。

> ⚠️ Node.js 25 では `next dev` が `localStorage.getItem is not a function` で 500 になります（Node 25 の Web Storage 実験機能が既定で有効なため）。`npm run dev` / `npm start` は `scripts/run-next.mjs` 経由でこの機能を無効にして起動するので通常は回避されますが、Node 22 LTS の利用を推奨します。

```bash
cd osaka-mfg-finder
npm install

# 環境変数（APIキーは任意。未設定でもCSV・閲覧・キーワード検索は使えます）
cp .env.example .env          # Windows: copy .env.example .env

npm run db:push               # SQLite（prisma/dev.db）を作成
npm run db:seed               # 架空データ（企業10・需要15・正解データ）を投入
npm run dev                   # http://localhost:3000
```

### 環境変数

| 変数 | 必須 | 説明 |
|---|---|---|
| `DATABASE_URL` | ✅ | `file:./dev.db`（SQLite） |
| `OPENAI_API_KEY` | 任意 | 未設定ならAIマッチングは無効。キーはサーバー側でのみ使用し、ブラウザには送りません |
| `OPENAI_CHAT_MODEL` | 任意 | 既定 `gpt-4o-mini` |
| `OPENAI_EMBEDDING_MODEL` | 任意 | 既定 `text-embedding-3-small` |

APIキーを設定していない場合、画面上部に「AI分析は無効」と表示され、AIマッチングのボタンは押せません。キーワード検索の結果は「名称一致の結果（AI分析ではない）」と明記して表示します。

### その他のコマンド

| コマンド | 内容 |
|---|---|
| `npm test` | 単体テスト（CSV・検証・キーワード検索・ベクトル類似度・Precision@K・出力の正規化） |
| `npm run verify:ai-mock` | **OpenAIをモックに差し替えて**AIパイプラインを通す検証（実APIは呼ばない、別DBを使用） |
| `npm run db:reset` | DBを消去して架空データを再投入 |
| `npm run build && npm start` | 本番ビルドで起動 |

## 3. 画面

| 画面 | できること |
|---|---|
| ダッシュボード | 登録企業数・登録ニーズ数（うち確定発注）・分析済み組み合わせ数・新用途候補数・評価件数。CSVアップロード／マッチング実行への導線 |

| CSV取り込み | 種別選択 → ファイル読込 → **プレビュー・検証**（エラー行、ファイル内重複、既存IDの上書き件数）→ 登録。テンプレートDL、エクスポート |

## 4. AIマッチングの処理（5段階）

```
企業CSV/需要CSV
   │
   ├─ STEP1 企業の構造化   … 技術名・加工方法・材料・機能・制約・強み（入力にない能力は追加しない）
   ├─ STEP2 需要の構造化   … 課題・機能・材料・加工方法・必須条件・希望条件・不明な条件
   ├─ STEP3 候補検索       … ①キーワード一致（名称ベース・ベースライン）＋②埋め込みのコサイン類似度（意味検索）
   │                          → 両方の上位Kの和集合を候補とする
   ├─ STEP4 適合性分析     … ペアごとにLLMが JSON で回答（理由・一致能力・応用可能性・ハード不一致・不明条件・確認事項・根拠）
   └─ STEP5 結果の正規化   … スコア範囲の補正、ハード不一致の処理、根拠の原文検証、保存（キャッシュ）
```

### 出力（1組の結果）

以下は**形式の例（値は架空）**です。

```json
{
  "supplier_id": "S-07",
  "demand_id": "D-03",
  "match_score": 88,
  "match_status": "candidate",
  "reason": "（AIの推測）ホブ切りによる歯車加工の能力が需要の技術要件と重なる",
  "matching_capabilities": ["歯車加工", "ホブ切り"],
  "potential_application": "（AIの推測）…",
  "hard_constraint_conflicts": [],
  "unknown_conditions": ["熱処理後の寸法保証の可否"],
  "questions_to_verify": ["JIS相当の精度の実績を確認する"],
  "evidence": [
    { "source_type": "supplier", "field": "processes", "excerpt": "ホブ切り、歯切り、歯面研削" }
  ],
  "dropped_evidence": 1,
  "mode": "ai",
  "model": "gpt-4o-mini"
}
```

### 守っているルール（コードで強制）

| ルール | 実装 |
|---|---|
| `match_score` は**探索優先度**（受注確率ではない） | UIとCSVの見出しで明示。スコアは0〜100に丸める |
| 必須条件が**明確に不一致**なら高評価にしない | `hard_constraint_conflicts` が1件でもあれば `match_status = excluded_hard_conflict`、スコアは20以下に抑える |
| 不明な条件は「適合」にしない | `unknown_conditions` として「要確認」に分類。適合という状態値は存在しない |
| 推測と事実を区別する | `reason` / `potential_application` は「AIの推測」と表示。`evidence` は**原文に実在する文字列のみ**残す。実在しない根拠は破棄し件数を表示 |
| 利用許諾のないデータを外部AIへ送らない | `licensed` / `fictional` 以外は埋め込み・構造化・分析の**いずれも送信しない**（エラーで返す）。キーワード検索は外部送信しないので対象外 |
| 個人情報・契約上の秘密を送らない | 同梱データは架空。取り込み時に個人情報欄はない。運用時は `licensed` 確認を人が行う前提 |

## 5. 需要の種類の扱い

| 種類 | 意味 | 画面での扱い |
|---|---|---|
| `order` | 実際の発注・調達案件 | 「確定した需要」として数えるのはこの種類のみ（ダッシュボードの「うち確定発注」） |
| `tech_search` | 企業が公開した技術探索ニーズ | 探索ニーズとして表示。発注は確定していない |
| `rnd_theme` | 研究開発テーマ | **確定発注として扱わない**。詳細画面と一覧で明示 |
| `hypothesis` | 将来の用途仮説 | **確定発注として扱わない**。「実在の需要を示すものではない」と明示 |

補助金採択情報や研究開発テーマを確定した発注需要として扱うことはしません。

## 6. 評価方法

### 6.1 人による評価（主な評価）
- 評価・比較画面で、AIの上位候補とキーワード候補それぞれに **有望／不適合／要確認** とコメントを付けて保存します。
- 研究発表では、「AIの候補が人手で有望と判断された割合」「キーワード候補との重なり」「不一致の検出が妥当だったか」を集計します（集計機能は未実装。CSVの評価をもとに手作業で行う想定）。

### 6.2 Precision@K（正解データがある需要のみ）
- 正解データ（`sample-data/ground_truth_sample.csv`）は**検証者が作成したもの**だけを使います。
- Precision@K = 上位K件のうち正解（`relevant = 1`）の割合。K = 5（既定）。
- 正解データが存在しない需要では**Precision@Kを表示しません**。
- 同梱の正解データは架空データに対する検証用の例で、性能の主張には使えません。

### 6.3 キーワード検索との比較
- キーワード検索は「需要の必要技術・材料」の語が企業の加工技術・材料・業種などの文字列に含まれる割合（一致率）です。
- 比較は同じ需要に対して、キーワード上位Kと AI 上位Kを並べて行います（評価・比較画面）。

### 6.4 同梱データの位置づけ
- 同梱の架空データは、以下の3パターンを含みます（期待される挙動の確認用）。
  1. **明確に適合**: D-01（精密切削・SUS304・小ロット）→ S-01 など
  2. **異業種で応用可能**: D-11（屋外筐体の板金）→ S-02（食品機械の板金） / D-14（微小電極）→ S-08（微細加工） など
  3. **必須条件が不一致**: D-08（φ600mmの歯車）→ S-07 は最大φ400mm / D-10（チタン・±0.005mm）→ 取り扱いなし / D-13（膜厚±0.5μm）→ S-04 は±2μm
- 正解データはこの3パターンを反映して作成しています（作成者による判断であり、実データの検証ではありません）。

## 8. 技術的制約・既知の課題

- **AIの推論品質は未検証**（上記）。LLMの出力は JSON モードで受け取るが、スキーマ違反への耐性は最小限（欠損は空配列、不正は0点扱い）。
- **ハード条件の判定はLLMに依存**。数値の公差比較などを決定的に行うルールエンジンは未実装。
- **意味検索はベクトルを SQLite に JSON で保存**し、全件をメモリ上でコサイン比較しています。数百件を超える規模は想定していません。
- **埋め込みはマッチング実行時に遅延計算**します。初回は件数に応じて時間がかかります。
- **AIマッチングは逐次実行**（候補数×LLM呼び出し）。候補数K=5で数十秒かかることがあります。
- **同時編集・認証なし**。ローカル単独利用を前提としています。
- **CSV取り込みは全件エラーなしの場合のみ登録**（部分登録はしない）。
- **編集・削除で関連する分析・評価を削除**します（企業・需要の変更は再分析が必要なため）。
- **評価の集計画面は未実装**（個別の評価と保存のみ）。
- **構造化結果（STEP1/2）は画面に表示していません**（DBに保存のみ）。
- **外部Webサイトからの取得機能は一切ありません**（仕様どおり）。
- **ニーズの鮮度（募集期限の切れ）の自動判定はしていません**（期限は表示のみ）。

## 10. 採用した初期値（不明点への判断）

| 論点 | 採用した値 | 理由 |
|---|---|---|
| 埋め込みモデル | `text-embedding-3-small` | 安価で十分な性能の既定値。環境変数で変更可 |
| 分析モデル | `gpt-4o-mini` | 低コストでJSON出力に対応。環境変数で変更可 |
| 上位K | 5（3／5／10 から選択） | 研究発表で画面に収まる件数 |
| 新用途候補 | AI候補・スコア60以上・企業の業種と需要の業界が異なる | 「異業種」の操作的定義 |
| 根拠の検証 | 原文に一字一句含まれる場合のみ採用 | 捏造された引用を排除するため |
| 利用許諾 | `licensed` / `fictional` のみ外部送信 | 未確認データの外部送信を防ぐため |
| スコア上限 | ハード不一致時は20 | 「高評価にしない」を明確に示すため |
| 取り込み | 1件でもエラーがあれば登録しない | 部分登録による混乱を避けるため |

## 12. 研究発表での見せ方（例）

1. ダッシュボード → 需要 **D-11（蓄電設備の屋外筐体）** を開く（種類：技術探索ニーズ）
2. マッチング → キーワード検索（例: D-08 → S-07 が一致率75%で上位）→ 名称が一致する企業が上位になることを見せる
3. AIマッチング（キー設定時）→ **S-02（食品機械の板金）** が異業種の応用候補として挙がるか、根拠の原文と「推測」の区別を見せる
4. 需要 **D-08（大型歯車）** → S-07 が「必須寸法φ600mmに対し最大φ400mm」で**ハード不一致**として扱われることを見せる
5. 評価・比較 → 有望／不適合／要確認を付けて、キーワードとAIの比較を見せる

> 上記のAI部分の挙動は、APIキーを設定した実環境で確認してから発表に使ってください（未検証の部分があります）。
